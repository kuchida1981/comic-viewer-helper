## Context

現在、このプロジェクトのテストは Vitest によるユニットテストに限定されており、ブラウザ特有の挙動や DOM 構造への依存（スクロール位置の計算、UIの注入、イベント発火など）を自動検証する手段がありません。
また、開発環境（OSやブラウザバージョン）の差異がテスト結果に影響を与えるリスクがあるため、完全に分離・固定された環境での検証が必要です。

## Goals / Non-Goals

**Goals:**
- Playwright を使用した、信頼性の高い E2E テスト基盤の構築。
- Docker による環境の完全な分離と再現性の確保。
- Nginx を使用したモックサーバーによる、対象サイトの挙動のシミュレーション。
- AI エージェントが失敗原因を容易に特定できるようなデバッグ情報の提供（Trace Viewer / Report）。
- ローカルおよび CI (GitHub Actions) での共通実行フローの確立。

**Non-Goals:**
- 複数ブラウザのサポート（当面は Chromium のみ）。
- 画像比較によるビジュアル回帰テストの導入。
- 本番サイトへの直接アクセスによるテスト。

## Decisions

### 1. Playwright の採用
- **理由**: 実行速度、強力なデバッグツール（Trace Viewer）、そして Docker との親和性が高いため。

### 2. Docker Compose によるオーケストレーション
- **サービス構成**:
  - `playwright`: テスト実行コンテナ。Node.js 環境とブラウザを含む。
  - `mock-server`: Nginx コンテナ。テスト用の HTML/画像を配信する。
- **理由**: ネットワーク分離により、テスト実行機からモックサーバーへの安定したアクセスを保証するため。

### 3. Dockerfile.e2e 内でのビルド実行
- **理由**: ホストマシンの `dist/` の状態に左右されず、常に最新のソースコードからビルドされた `user.js` をテストするため。

### 4. Nginx による静的ファイル配信
- **理由**: 超軽量であり、`/magazine/123/` のような実際のサイト構造をディレクトリ構成で簡単に模倣できるため。

### 5. AI フレンドリーなデバッグ情報の永続化
- **理由**: `./playwright-report` をホストマシンにマウントし、トレース情報を残すことで、AI が失敗時の DOM 状態を後から解析できるようにするため。

## Risks / Trade-offs

- **[Risk] Docker ビルド時間の増大** → **[Mitigation]** `node_modules` のキャッシュを効かせる Dockerfile 構成にする。
- **[Risk] アニメーションによる Flaky テスト** → **[Mitigation]** テスト実行時は CSS でスムーズスクロールを無効化し、Playwright の `waitFor` 機能を適切に使用する。
- **[Risk] Git 情報の欠落** → **[Mitigation]** `scripts/build.mjs` が `.git` がない環境でも動作するように調整する。
