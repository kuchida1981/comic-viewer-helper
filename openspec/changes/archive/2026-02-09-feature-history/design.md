## Context

現在の検索モーダル (`SearchModal.ts`) は検索機能に特化しており、コード量も増加しています。閲覧履歴や傾向分析を追加するにあたり、これらを単一のコンポーネントで管理すると保守性が低下するため、タブベースの疎結合な設計への移行が必要です。また、データの永続化には大容量かつ非同期操作に適した IndexedDB を採用します。

## Goals / Non-Goals

**Goals:**
- IndexedDB を用いた作品閲覧履歴の永続化。
- 最近閲覧した作品のリスト表示（時系列）。
- 全履歴からのタグ出現頻度の集計とランキング表示。
- 検索モーダルを「マルチ機能モーダル」へ拡張するためのタブシステムの導入。

**Non-Goals:**
- 履歴のクラウド同期（完全にローカルのみ）。
- 閲覧時間に応じた重み付け集計（今回は単純な出現回数とする）。
- 作品ごとの既読ページ数の詳細なトラッキング（ResumeManager の役割とする）。

## Decisions

### 1. HistoryManager の新設と IndexedDB のラップ
DB操作を抽象化する `HistoryManager` を作成します。
- **理由**: `Store` に直接 DB 操作を書くと複雑になるため。`idb` のような軽量ライブラリを使わず、標準の `indexedDB` API をラップしたシンプルなユーティリティを作成します。
- **スキーマ**:
  - `history` ストア: `url` (key), `title`, `thumb`, `tags`, `lastViewedAt`

### 2. コンポーネントの分割 (リファクタリング)
`SearchModal.ts` を以下の構成に分割します。
- `SearchModal.ts`: モーダル全体の枠組みとタブ切り替えを管理。
- `SearchTab.ts`: 既存の検索UIとロジック。
- `HistoryTab.ts`: 履歴リストの表示。
- `AnalysisTab.ts`: タグランキングの表示。

### 3. 集計ロジックの実行タイミング
タグのランキング集計は、**分析タブが開かれた時**に非同期で実行します。
- **理由**: 履歴が増えた場合に `App.init` で毎回集計すると起動パフォーマンスに影響するため。集計結果は必要になるまで計算しません。

### 4. タブ状態の管理
現在の選択タブは `Store` ではなく、`SearchModal` の内部状態（または UI のみの管理）とします。
- **理由**: モーダルを閉じた後にタブ位置を復元する必要性は低く、グローバルな状態にするメリットが少ないため。

## Risks / Trade-offs

- **[Risk] IndexedDB の互換性/不具合** → [Mitigation] 基本的な CRUD 操作に限定し、エラー時はコンソール出力に留め、アプリ全体の動作を妨げないようにガードします。
- **[Risk] 大量履歴による集計負荷** → [Mitigation] 履歴の最大保存件数（例: 1000件）を設け、古いものから自動削除する仕組みを検討します。
- **[Risk] モーダル内のレイアウト崩れ** → [Mitigation] タブのコンテンツ量に応じてモーダルの高さを柔軟に調整するか、内部スクロールを適切に設定します。
