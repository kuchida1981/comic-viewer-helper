## Context

ESLint 厳格化 Phase 1 & 2 を経て、基本的な静的解析とデータ境界の型安全化が完了しました。
しかし、現状では以下の課題が残っています：
- `this` 束縛の安全性が `constructor` 内の `bind` という手動かつ冗長な手段に依存している。
- テストコードにおいて、Vitest モックの `any` 性を理由に一部の不安全ルールが緩和されており、テストコード自体の品質がプロダクションコードに劣る。
- `no-confusing-void-expression` 等の厳格な型チェックが未適用であり、微細なバグの温床となる可能性がある。

## Goals / Non-Goals

**Goals:**
- クラスメソッド定義をアロー関数プロパティに統一し、`this` 束縛を言語仕様レベルで安全にする。
- プロダクションコードおよびテストコードの両方で、ESLint の厳格なルールを 100% 適用する。
- テストコードにおける `any` 起因の不安全操作を根絶し、モック周りの型安全な記述パターンを確立する。

**Non-Goals:**
- UI コンポーネントの構造や CSS スタイルの変更。
- 新機能の追加。
- Vitest 自体のアップデート。

## Decisions

### 1. アロー関数プロパティ (Class Property Syntax) への移行
全クラス（Manager系, Store等）のメソッド定義を、通常のメソッド定義からアロー関数プロパティに変更します。
- **理由**: インスタンス化時に自動的に `this` が固定されるため、`bind` の書き忘れや `unbound-method` エラーを本質的に回避できる。
- **代替案**: `constructor` での `bind` の徹底。しかし、新しくメソッドを追加するたびに追記が必要なため、保守性が低い。

### 2. テストコードにおける `no-unsafe-*` ルールの再適用
`eslint.config.mjs` でテストファイル（`**/*.test.ts`）に対して設定していたルールの緩和を削除します。
- **アプローチ**: 
    - `vi.mock` の戻り値や `vi.fn()` の引数を、インターフェースや `Mock` 型を用いて明示的にキャストする。
    - プロパティアクセス時には、事前に型ガードや Null チェックを行う。
    - どうしても型が解決できない極小の箇所に限定して `// eslint-disable-next-line` を理由付きで使用する。

### 3. `void` 式と不要な条件の整理
`no-confusing-void-expression` と `no-unnecessary-condition` を有効化し、既存コードを修正します。
- **アプローチ**:
    - `void` を返す関数の戻り値をそのままアロー関数の戻り値として返さない（ブロック `{}` で囲むか、明示的に `void` 演算子をステートメントとして使う）。
    - 型情報に基づき、常に truthy/falsy な条件分岐（`if (arr)` などで `arr` が常に `[]` である場合など）を削除または修正。

## Risks / Trade-offs

- **[Risk] テストコードの修正コストが非常に高い**
    - **Mitigation**: 共通のモックパターン（例：`as unknown as SomeType` ではなく `MockInstance` の利用）を確立し、同様の修正を水平展開する。
- **[Trade-off] バンドルサイズの微増**
    - アロー関数プロパティは、プロトタイプメソッドではなく各インスタンスのプロパティとして展開されるため、ごく僅かにメモリ消費量が増える可能性がある。
    - **Mitigation**: 本プロジェクトのクラス数は少なく、インスタンスも基本シングルトン（1つのみ生成）であるため、実質的な影響は無視できる。
