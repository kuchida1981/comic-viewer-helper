## Context

現在、プロジェクトでは ESLint の厳格化を段階的に進めています。Phase 1 では基本的なルールの適用を完了しましたが、型安全性を著しく損なう `any` 経由の不安全な操作（unsafe rules）は一時的に `off` にされていました。

現状、`JSON.parse` や `localStorage.getItem` の戻り値をそのまま利用しており、ランタイムで予期しないデータ構造が渡された場合にエラーが発生するリスクがあります。また、テストコードにおいても `any` が多用されており、リファクタリング時の安全性が十分に確保されていません。

## Goals / Non-Goals

**Goals:**
- `@typescript-eslint/no-unsafe-*` ルールを `error` として有効化する。
- 外部データ（`localStorage`, `JSON.parse`）の境界に型検証（Type Guard）を導入し、型安全を保証する。
- テストコード内の不安全な `any` 操作を排除し、テスト自体の信頼性を高める。
- プロダクションコードにおける「0 エラー、0 警告」の状態を維持する。

**Non-Goals:**
- ロジックの大幅な変更やリファクタリング。
- サードパーティライブラリ（`vitest` 等）内部の型定義の修正。
- スタイルに関するルールの適用（Phase 3 で実施予定）。

## Decisions

### 1. `src/type-guards.ts` の新設
型検証ロジックを再利用可能にするため、専用のファイルを作成します。
- **理由**: `store.ts` や `ResumeManager.ts` で同様の検証が必要になるため。
- **代替案**: 各ファイルにインラインで書く（コード重複が増えるため却下）。

### 2. `JSON.parse` の戻り値を `unknown` として扱う
`JSON.parse` の戻り値を一度 `unknown` 型の変数に代入し、Type Guard を通してから目的の型にキャストします。
- **理由**: TypeScript のデフォルトでは `any` が返されるため、意図的に型安全なフローに引き込む必要がある。

### 3. テスト用モックの型安全性向上
`as any` によるモック作成を避け、必要最小限のインターフェースを実装するか、ヘルパー関数を利用します。
- **決定**: `jsdom` 環境で作成可能なものは `document.createElement` 等の実体を利用し、どうしてもモックが必要な場合は `Partial<T>` を活用する。

## Risks / Trade-offs

- **[Risk] テストコードの修正量が膨大 (約190件)**
    - **Mitigation**: 共通のヘルパー関数や Type Guard を用意し、パターン化した修正を行うことで効率化する。
- **[Risk] ランタイムでのデータ不整合による挙動の変化**
    - **Mitigation**: 現在の不完全な検証（`typeof pos.left !== 'number'` 等）を維持しつつ、Type Guard に移行することで、検証漏れを防ぎ、不整合時には安全なデフォルト値（`null` や `{}`）を返すようにする。
- **[Trade-off] 記述量の増加**
    - 型安全性を確保するために Type Guard の定義と呼び出しが必要になるが、将来的な保守性を優先する。
